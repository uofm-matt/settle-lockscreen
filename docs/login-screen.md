# The login screen (GDM greeter)

The system install, `tools/pack.sh login`, takes `extension-login.js` as its `extension.js`. In GNOME Shell's `gdm` session mode it builds a `Greeter` instead of a `LockScreen`, and in a user session a `LoginFrame` next to the `LockScreen`. The clip plays from its first frame, which should be the picture the greeter already shows, for `lock-play-seconds` of display-on time, then fades back to that picture and mpv exits. It plays again the next time the display wakes. Every failure ends at the picture that was already there.

The greeter has no wallpaper actors, so the video layers go into the login dialog's parent, just below the dialog: over whatever draws the greeter's background, under the dialog and anything raised above it. When something else is added there later, the layers are moved back under the dialog.

When the password is accepted, GDM switches to the user's session within a fraction of a second, too soon for a slow-down. So `greeter.js` holds the dialog's start call for that one login: the video plays on for `settle-delay-ms`, slows over `settle-ramp-ms`, pauses, and mpv saves the frame; then the call goes ahead. With the defaults, signing in takes about 2.7 s longer; `settle` set to false skips it. A timer that nothing else cancels makes the call at the latest `settle-delay-ms + settle-ramp-ms + 2 s` after the password, and any failure makes it at once, so a broken hand-off never stops anyone signing in.

The frame reaches the user's session through `/run/settle-lockscreen-login/`, as `<uuid>.png` and `<uuid>.json`. The .json holds the position, the user name and the clip's identity (its size and a hash of its first and last 64 KiB), and is written last. The directory is made at boot by the system install: owned by root, group `gdm`, mode 2775. Each greeter is a new uid in the `gdm` group, so the next greeter can clear stale files, and no other user can create or claim the path. At login, and only if the desktop picture is already the extension's, the session takes the newest frame from the last two minutes that names its own user and the same clip. `takeFrame.js` does that as the user before the shell starts, so the session's first picture is the frame; if it did not run, the shell takes the frame itself a moment after it appears and crossfades to it. If the extension is enabled before the shell's startup animation begins, and the wallpaper is the extension's, that animation is skipped, so the session shows the frame at once instead of growing out of it. In tests that held on Fedora; Ubuntu enables its own extensions first, so the animation still runs there. A session that starts in the overview shows the frame as the workspace behind it.

The frame and the user name stay readable by every local user until a login more than two minutes later leaves its own frame, which clears the older ones, or the machine restarts. So the greeter's clip should be one every user may see, as one under `/usr/local/share` is. Login names are visible through `loginctl` anyway. Any process in the `gdm` group can write there, so the session decodes only regular files that name its own user and its own clip.

## What a system install needs

Nothing in this repository does this; whatever installs the extension system-wide must.

- The extension in `/usr/share/gnome-shell/extensions/settle-lockscreen@uofm-matt.github.io/`: the contents of `settle-lockscreen-login.zip` from `tools/pack.sh login`, with `glib-compile-schemas` run on its `schemas` directory there. Everything readable by the greeter user. That zip's `metadata.json` lists `gdm` in `session-modes`, and it has a second schema, `org.gnome.shell.extensions.settle-lockscreen.login`, for the login screen's own settings.
- `settle-lockscreen-login.service` from the zip in `/etc/systemd/user/`, enabled for every user with `systemctl --global enable settle-lockscreen-login.service`. It runs `takeFrame.js` from the extension's directory before each GNOME session starts, and does nothing for a user without `~/.local/share/settle-lockscreen`. A user manager already running when it is enabled picks it up only after it restarts (a reboot, or logging out fully) or after `systemctl --user daemon-reload`.
- `/etc/tmpfiles.d/settle-lockscreen.conf` containing `d /run/settle-lockscreen-login 2775 root gdm -`, applied once with `systemd-tmpfiles --create /etc/tmpfiles.d/settle-lockscreen.conf` and at every boot after. Without it the login screen still plays and signs in, but leaves no frame.
- No copy of the extension in a user's `~/.local/share/gnome-shell/extensions/`. Both builds have the same UUID and the shell loads the user's copy first, so for a user with any copy there, the extensions.gnome.org build included, the session runs that copy: the unit below still puts the login frame in place, but the session's own fallback and the change to the startup animation are lost.
- The clip where the greeter can read it, by default `/usr/local/share/settle-lockscreen/clip.mp4`.
- A dconf profile for gdm that reads `system-db:gdm`. Fedora's packaged profile already does; Ubuntu 26.04 and 26.10 need `/etc/dconf/profile/gdm` with `user-db:user`, `system-db:gdm` and their `file-db:` line.
- A file in `/etc/dconf/db/gdm.d/`, then `dconf update`, with `[org/gnome/shell]` `enabled-extensions=[...]` and `disable-user-extensions=false`; under `[org/gnome/shell/extensions/settle-lockscreen]` any of `video-path`, `lock-play-seconds`, `settle-delay-ms`, `settle-ramp-ms`, `hardware-decoding` and `play-in-power-saver`; and under `[org/gnome/shell/extensions/settle-lockscreen/login]` any of `dim` (0 to 1) and `settle` (true or false). dconf does not merge a key across files, so `enabled-extensions` must be one list holding every greeter extension.
- The greeter's picture set to the clip's first frame (`picture-uri` and `picture-uri-dark` of `org.gnome.desktop.background` in that gdm database), at a path the greeter can read. Otherwise the video fades in over a different picture.

Not tested: plugging in a monitor while the greeter is up, and hardware decoding as the greeter user on a real GPU.
